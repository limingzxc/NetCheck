# 审查：v2.6.1 发布版「所有 DNS 无响应」逃逸缺陷

- 对象：`8fd5703`（chore: 审查 P2 清理与清单/记录收口）引入，`d60b3a4` 打成 v2.6.1 发布
- 审查人 / 日期：AI 辅助审查（WorkBuddy AI）· 2026-10-13
- 门禁：`check.py` 通过（1260 通过 / 0 失败）、`check.py --e2e` 通过（119 通过 / 0 失败）
- 结论：修复完成，回归测试先红后绿

## 症状

发布版（standalone 与 lite 均复现）跑 DNS 检测时，界面显示「所有公共 DNS 都没有响应」，
四台服务器（223.5.5.5 / 119.29.29.29 / 114.114.114.114 / 8.8.8.8）全部失败。
导出 JSON 里每台都是同一个错误：

```
"Cannot send packets to an arbitrary host"
```

这不像网络故障。同一个程序里系统解析器（`DnsResolve`）四项全部正常，
说明本机 DNS 是通的，只有「直接向指定服务器发 UDP 查询」这条路断了。

## 根因

`8fd5703` 为修上一条审查发现（UdpClient 未 Connect、可能收到任意源地址的响应），
给 `DnsProbe` 的三处 UDP 探测都加了 `udp.Connect(server, 53)`。

但发包仍调用的是带端点的重载：

```csharp
udp.Connect(server, 53);
await udp.SendAsync(query, query.Length, server, 53)   // 冲突
```

`HttpClient` 和 `TcpClient` 的直觉是「连上之后再传一次地址也无妨」，UDP 不是这样。
`UdpClient.SendAsync(byte[], int, string, int)` 内部走 `Socket.SendTo`，
而已连接的 socket 不允许指定目标，于是抛 `SocketException`：

> Cannot send packets to an arbitrary host

错误信息里那句「arbitrary host」说的就是这个：socket 已经绑定了唯一对端，你又给了一个地址，它不认。

字符串在 `System.Net.Sockets.dll` 里（8.0.2 / 8.0.10 / 10.0.12 三个运行时都有），
与故障机器上的报错完全一致，确认不是环境个例。

## 为什么可归结为「逃逸」

- 回归测试没有覆盖这条路径。v2.6.1 从 1220 增加到 1255 条断言，其中
  `DnsProbe` 只有对 `ParseResponse` / `BuildQuery` 的纯逻辑断言，
  没有一条真的跑过「发出去、收回来」。Review 的第四节要求「修 bug 必须带回归测试」，
  但上一次 `Connect` 的改动本身就是在补 P2，没人给它配一条能覆盖收发的断言。
- 结论条自身把故障吞掉了。`ReportView.cs` 的 `best == null` 分支写的是
  「所有公共 DNS 都没有响应」，色调 `Neutral`。设计上这是对的（公共 DNS 用户没在用，
  不该标红），但结果是四台同时失败和一个正常但全部超时的网络，界面上一模一样，
  用户看到的是一句平静的中性结论，不是「程序出错了」。
- 错误串被截到 40 字符后仍能一眼看出异常，但导出报告里它混在一堆正常数据中，
  没有触发任何告警路径。

## 修复

把三处重复的「建 socket → 发包 → 收包 → 解析」收敛成一个共用助手 `QueryAAsync`，
`Connect` 之后统一用不带端点的重载：

```csharp
udp.Connect(server, port);
await udp.SendAsync(query, query.Length);
```

调用方 `TestServerAsync` / `ProbeHijackAsync` / `ProbeCompareAsync` 全部改走这一个入口，
顺带把原来抄了三遍的 try/catch 与解析逻辑也一并去重。

`TestServerAsync` 增加可选的 `port` 参数（默认 53），供单元测试在回环端口上验证收发；
正常调用方不传，行为不变。

## 回归测试（先红后绿）

新增 `CoreTest/Tests.cs` 的 `DnsProbeLoopback` 组：在 `127.0.0.1` 的临时端口上起一个
假 DNS 应答器（收到查询就回一条带 A 记录的应答），验证 `TestServerAsync` 能收发并解析出地址。
只走回环，不依赖外网、不受 DNS 环境影响，且毫秒级完成。

先确认它能失败（把有 bug 的发包方式临时放回去），实测结果：

```
单元测试：1257 通过 / 3 失败
  ✗ [DnsProbe 收发（回环）] 回环 DNS 应答应判成成功（实际报错：Cannot send packets to an arbitrary host）
  ✗ [DnsProbe 收发（回环）] 应答里的 A 记录要被解析出来   → 期望 1，实际 0
  ✗ [DnsProbe 收发（回环）] 回环应答器不应报错   → 期望 ""，实际 "OperationCanceledException"
```

报错串与线上完全一致。恢复修复后：1260 通过 / 0 失败。

## 验证

- `check.py` 通过，1260 通过 / 0 失败
- `check.py --e2e` 通过，119 通过 / 0 失败
- 真实网络（Release 构建 + 两个发布版 exe 各跑一次 `--check dns`）：

```
当前 DNS        223.5.5.5 2.1 ms / 119.29.29.29 0.9 ms（各 2 条应答）
对比 DNS        223.5.5.5 1.5 / 119.29.29.29 1.3 / 114.114.114.114 1.1 / 8.8.8.8 0.9 ms
劫持检测        四台全部 Ok，rcode=0
域名解析        四个域名全部 Ok
```

standalone 与 lite 两个 exe 结果一致。

## 逃逸分析（按第八节）

- 第五节清单里哪一条本可以拦住它？没有。清单要求「修 bug 带回归测试」，
  但没要求「涉及网络收发的改动必须有回环测试」。补一条：
  *改动 `Core/` 里任何 socket 收发路径时，测试要能在回环上跑通一次真实收发，不能只断言解析函数。*
- 它是被什么放过去的？测试盲区（纯逻辑断言覆盖不到 socket 调用）
  加上结论条设计（中性色把「程序故障」渲染成了「网络现状」）。

## 附带记录

同一个错误在 `StunAndNat.cs` 里不存在。那里先 `udp.Connect` 到固定 STUN 服务器，
发包用的是不带端点的重载（`SendAsync(request, request.Length)`），
所以「Connect 后不能用带端点重载」这条规则在那个文件里本来就被遵守了，
只有 `DnsProbe` 这次新加的代码踩了坑。已把这条规则写进 `QueryAAsync` 的注释里。
